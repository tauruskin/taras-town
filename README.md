# Taras Town

A friendly little open-world town you can wander around, made for a 6-year-old.
Top-down view, touch controls, no violence, nothing scary — just a bright
cartoon town with houses, shops, parks, a market, and a wide estuary you can
swim in, with islands, boats to save up for, and quiet music playing.

**Play:** https://tauruskin.github.io/taras-town/

---

## How it's built

Plain HTML, CSS and JavaScript. No framework, no build step, no dependencies.
**The files in this repository are exactly the files that get served** — what
you see here is what runs on the phone.

Nothing is loaded from another website, and there are no image or sound files:
every tree, house, boat and character is drawn with shapes by the code, and
every sound is generated live. That keeps the whole game tiny and means nothing
can break because an external service changed. (The one exception is the
home-screen icons in `icons/`, and even those were generated by a script in
`tools/`.)

There is no server, no database and no account. The only thing stored is a bit
of progress in the browser's own `localStorage`, which never leaves the phone.

## Installing it

On the phone, open the game once with the internet on, then:

- **Android (Chrome):** the browser menu offers "Add to Home screen" or
  "Install app".
- **iPhone (Safari):** tap the Share icon, then "Add to Home Screen". This
  only works from Safari — Chrome on iPhone cannot install a web app; that is
  an Apple restriction, not something this game can work around.

Once installed it opens full screen from its own icon, with no browser
address bar, and — after that first online visit — **it opens with no
internet connection at all.** A phone in flight mode, or a car with no
signal, still plays the game exactly the same.

Updates still arrive the normal way: whenever the installed app is opened with
any connectivity, it quietly fetches whatever was last pushed. It only falls
back to the offline copy when there truly is no connection.

## Controls

On a phone: the joystick on the **left half** of the screen (grab it anywhere),
and four things in the corners.

| Where | What |
|---|---|
| Bottom right | The action button — get in and out of a car or boat, take a job. |
| Top right | A house (back to the opening screen), a speaker (sound off), and a palette (the shop). |
| Below those | The map of the town, with a dot for where you are. |
| Top left | How many coins you have. |

The speaker silences **everything**, and being switched off is remembered
between visits. It stays in the same corner whether the menu is open or not,
because a mute button you have to go looking for is not much use.

On a computer, for testing:

| Key | Does |
|---|---|
| `W` / `A` / `S` / `D` | Up / left / right / down. Arrow keys work too. |
| `Space`, `E` or `Enter` | Get in or out — the same as the round button. |

The keyboard produces the same direction the joystick does, rather than being
wired in separately. So on foot it's the way he walks, and in a vehicle it's the
heading it steers towards — one control model, whichever you use.

> **Known quirk on a laptop.** The game listens for `W`/`A`/`S`/`D` everywhere
> and swallows them, so those four letters cannot be typed into the name box on
> a computer. Every other letter works, and so does the whole alphabet on a
> phone, which is where the game is actually played. Left alone deliberately.

## Running it on your own computer

The JavaScript uses ES modules, which browsers refuse to load from a
double-clicked file. Serve the folder instead:

```
python -m http.server 8777
```

Then open <http://127.0.0.1:8777/> and press play.

To see the whole town at once — useful whenever the map generation changes —
open <http://127.0.0.1:8777/tools/map.html>.

## Checking nothing broke

```
node tests/run.mjs
```

Starts a web server and two browsers, runs **32 suites**, and shuts everything
down. Nothing to install. After a deploy, `node tests/run.mjs --live` runs the
same checks against the real site — which catches things a local copy never
will.

See `tests/README.md` for what each one covers.

### Want to change something?

Almost everything worth adjusting lives in **`js/config.js`** — walking speed,
swimming speed, how zoomed-in the camera is, the size of the joystick, every
colour, every vehicle. Change a number, reload the page.

To change the **size or shape of the town**, see "The town is generated" below.

## Notes for whoever works on this next

- **Never use a leading `/` in a path.** GitHub Pages serves this from
  `/taras-town/`, so `/css/style.css` would look for it at the top of the whole
  site and silently fail. Relative paths only.
- The game is landscape-only. Phone browsers ignore the JavaScript
  orientation-lock API (iPhone Safari has never supported it), so the thing that
  actually enforces this is the CSS overlay in `style.css`.
- **Look at it.** Most of the bugs worth finding in this project were found by
  rendering a screenshot and looking, not by an assertion. Several were
  invisible to a passing test suite: trees planted in tidy rows, a lake that did
  not exist, a colour that could not be tapped, road markings that slid along
  the road. `tools/map.html` exists for exactly this.

## The town is generated

The whole town comes out of two numbers — `MAP_COLS` and `MAP_ROWS` in
`js/config.js`, currently **96 × 72 squares of 64 pixels**, so 6144 × 4608. Of
that, **42% is water and 58% is land** — set by `RIVER_TILES` in `js/world.js`,
which is how wide the estuary down the right-hand side is. The
roads, the blocks between them, the houses that fill those blocks, which blocks
are left as parkland, where the market goes, the river, its islands and the
lake are all worked out from that size. Making the town bigger is a matter of
changing those two numbers and nothing else.

All of it is deterministic: the same numbers in give the same town out, every
time, on every device. That is what lets two phones play together without ever
sending a word about the map — they are already looking at the same town. It is
also why nothing about the map is saved.

The generation lives at the top of `js/world.js` and runs in this order, which
matters more than it looks:

1. `_plan()` — where the roads run, and which blocks are parks.
2. `_buildGrid()` — grass, then the river and its islands, then the parks, then
   **the lake**, then the roads, then the pavements. The lake has to come after
   the parks: carved before them, the park was painted straight over the top and
   there was simply no lake, with nothing on screen to say so.
3. Buildings, park props, trees.
4. **`_collectSolids()` and `_indexSolids()`** — the walls, gathered *before*
   the hiding places, so each one can check a player could actually stand in it.
5. Hiding places on land, then in the water.
6. The spawn point — last, because it needs to know where the cover is.

Collision goes through a coarse grid of buckets rather than walking the whole
list of walls. With twelve times as many walls as the old hand-drawn map, it is
**faster** than it used to be: 200,000 overlap tests went from 20ms to under
10ms, with roughly nine times as many walls to check.

## Where the game starts

The spawn point is fussier than it looks, and every rule on it was added
because something went wrong without it. It must be near the middle of town, on
dry land, **not under a bush**, and with room to walk off in any direction.

- Under cover, two children starting a game together cannot see each other, and
  the first thing either sees is an empty town.
- A gap it merely *fits* in is not enough: a slot between two walls means
  pressing the stick and not moving.
- Nothing parks or stands within 130px of it either. With sixty-odd cars and a
  dozen neighbours, one lands right on top of the spawn — and a neighbour is
  solid, so that is a wall across the first direction anybody pushes.

## Hiding places

The game is mostly used for hide-and-seek, so cover is a feature rather than
scenery. There are around **460 trees and 1,200 other pieces of cover**, in nine
kinds. Most of that count is lily pads and reeds, because the water is now
nearly half the map:

| On land | In the water |
|---|---|
| Bushes, everywhere green | Lily pads, out in the open water |
| Bus shelters along the pavements | Reeds in the shallows |
| A market of striped stalls in one park | Jetties running out from the bank |
| A bandstand in the town park | Rowing boats moored at some of them |
| Parasols dotted about the parks | |

**None of it is solid.** You walk in and the thing is drawn over the top of
you — that is the bit that makes hiding work, and it is why a piece of cover you
bounce off is a bug rather than scenery. Tree trunks are the one exception, and
only the trunk.

Cover is only ever placed somewhere a player could actually stand, which is why
the walls are gathered before it is put out. Nineteen pieces were sitting inside
scenery before that was fixed: perfectly visible, and impossible to get into.

**Names go out under cover.** A label hanging over the bush somebody is crouched
in would give away the hiding place the bush exists to provide.

## Swimming

Water is not solid for people, so wading in and climbing out is just walking —
there is no special code at the water's edge, which is where all the ways to get
stuck would otherwise live. He swims at about three fifths of running speed.

He puts on **armbands**. A game that tells a six-year-old the river is great fun
can just as easily tell him what you put on first, and from directly above a
bright orange ring is the clearest thing on him.

There is no drowning, no timer and no way to fail. `tests/offline/swimming.mjs`
checks the thing that would actually matter: from every one of the water tiles,
in four directions, there is always a way back to dry land.

## Music

There is no music file. The tune is a few lines of note data played through the
same oscillators that make the game's other sounds, so it adds **nothing at all**
to what the phone downloads, works with no connection, and leaves nothing
permanent in the repository.

That last point is not theoretical here: a 14MB MP3 was once committed to this
project, and git keeps history for ever — the file was still in the repository's
weight after being deleted, and the fix in the end was to restore from a backup.
A properly compressed loop would be a few hundred kilobytes rather than
fourteen megabytes, but it would still be downloaded on install and still be
permanent.

How it is meant to sound: quiet, slow and a bit dreamy, something that can play
under a game for hours without anybody noticing it. Three things do most of that
work — everything is in a **major pentatonic** scale, which has no semitone
steps, so nothing picked from it can sound wrong against anything else; the
melody is **sparse**, and plenty of bars have only a note or two in them; and it
**never repeats exactly**, because each bar is improvised rather than looped, so
there is no seam to start listening for.

**One button turns everything off**, music and sound effects together. Two
buttons would be tidier for an adult and worse for a 6-year-old, who wants "make
it quiet". The music also stops whenever the game is not on screen, because
playing to a pocket costs battery.

If a real recording is ever wanted instead, `js/music.js` is the only file that
would change: `startMusic` / `stopMusic` / `setMusicMuted` is the whole of what
the rest of the game knows about it.

## Vehicles

They live in `CONFIG.VEHICLES` in `js/config.js`, in the order they appear in
the shop.

| | Price | |
|---|---|---|
| Car, van | free | |
| Jeep | 100 | quick off the mark, tight round a corner |
| Sports car | 200 | fast and darty |
| Monster truck | 300 | |
| Bus | 400 | slow, very long, a job to turn round |
| **Speedboat** | **500** | floats |
| **Ferry** | **600** | floats, and is enormous |

Each entry carries its own size, top speed, acceleration, turning rate and
price, so adding another means one entry there and one `case` in `Car.draw`.

**A boat is the exact opposite of a car.** Wheels are stopped by water; a hull
is stopped by land. Both are checked at the corners as well as the middle, so a
ferry cannot beach its bow while the rest of it floats. `moveBox` takes a
terrain of `null` (a person, who minds neither), `'land'` or `'water'`.

**Boats are chosen separately from cars.** They share the shop row, but buying a
speedboat must not turn the car parked on the road into one — so the save
remembers a chosen boat *and* a chosen car, and whichever you board takes the
right one. Boats lie moored in the water from the start whether or not anybody
owns one, because seeing a speedboat tied up out there is the reason to save for
it; walking up to one before buying does nothing.

**They have two different sizes.** `half` is the square used to move around
town, scaled from the vehicle's width — small and forgiving, so nothing ever
wedges on a corner. `boundsBox()` is the real footprint that everything else
collides with. Making them the same would either let the player stand on the
bonnet or make the bus impossible to drive.

**Swapping vehicles can fail.** A bus does not fit everywhere a hatchback does,
so `setVehicle` checks whether the new shape fits where the old one was
standing, nudges it to the nearest place it does, and if there is nowhere at
all, refuses the change rather than leaving it embedded in a wall. That last
path is deliberately exercised by `tests/offline/vehicles.mjs`, because an
untested safety net is not a safety net.

### Getting out

Harder than it sounds, and it was wrong three ways at once. Getting out used
to drop the player inside a building often enough to be the first bug reported
from real play. All three causes are worth knowing, because they are easy to
reintroduce:

- **The vehicle itself counts.** While driving it is not in the way; the instant
  you are out it is solid like anything else, so a spot overlapping it is a
  trap, not an exit.
- **How far to step depends on the direction.** Stepping out sideways only has
  to clear the width; stepping out behind has to clear the length. Using the
  width for both put anyone leaving a bus inside the bus.
- **Four places is not enough.** Parked snugly, all of left, right, behind and
  in front can be blocked — and the old code then gave up and returned the
  vehicle's own centre, which is the worst possible answer.

It now tries sixteen directions at four distances, falls back to a proper
outward search, and if there is genuinely nowhere it says so and keeps the
player in the vehicle. Staying in is recoverable; being put down inside a wall
is not. `tests/offline/getting-out.mjs` tries 5,000 ways out and fails five ways
against the old code.

## The minimap

The town is about forty screens across, which is easy to get lost in. The map
never changes, so it is painted **once** into an offscreen canvas and stamped
into the corner each frame — redrawing nine thousand tiles every frame to fill a
hundred pixels would be a silly way to spend a phone's battery.

**Only you are on it.** Not the other players: this game is mostly hide-and-seek,
and a map with everybody's position on it would end that in about four seconds.

## Adding a colour to the menu

Add an entry to `HAT_PALETTE`, `SHIRT_PALETTE` or `CAR_BODY_PALETTE` (plus the
matching `CAR_ROOF_PALETTE` entry) in `js/config.js`. The menu builds its rows
from the length of those lists, so a new dot appears on its own and the row
re-spaces itself to fit.

Choices are saved as **positions in those lists**, not as colour strings. So
editing a palette entry restyles everyone who had picked it, rather than leaving
old saves pointing at a colour that no longer exists.

One trap, since fixed and worth not re-digging: the menu rows used to start at a
fixed fraction of the screen height. On a short landscape phone that put the top
row underneath the corner buttons, and the last hat colour could not be chosen
at all — the tap landed on the done button instead. Nothing looked wrong.
`tests/offline/menu-buttons.mjs` now presses the middle of every button at seven
screen sizes and checks the right one answers.

## Where jobs send you

Delivery addresses and hiding places are **worked out from the map when the game
starts**, not typed out as coordinates. Every house's doorstep is taken from the
building itself, so adding a building gives it a delivery address for free.

Both lists are filtered on *openness* — the fraction of directions you can walk
away from a spot. Anything below 45% is dropped.

This matters more than it sounds. An earlier version listed destinations as
literal coordinates. Several were **inside buildings**, and `findFreeSpot`
quietly rescued them by shifting up to 182px, so a "front door" was nowhere near
a door. Two others sat in gaps only 8% open: reachable on paper, but a child
would just bump around in them. Hand-typed coordinates rot as the town changes;
derived ones cannot.

## How a job works

Every job is the same thing underneath: a **list of places to reach, in order**.
Most have one. The race has four, and reaching one lights up the next. That is
the only difference between a delivery and a race — there is no separate race
code path.

Nothing can be failed and there is no timer, not even on the race. A child who
wanders off to look at the river comes back to a job still waiting.

There are **twelve neighbours**, three of each kind of job: a few within a short
walk of where the game starts, so a job is found almost at once, and the rest
spread right across the map with a long way between them. `lastPick` is per job
*type* rather than per person, so several people offering the same job still
send you somewhere different each time.

To add a fifth kind: add a `mission` name to `PEOPLE` in `js/npc.js`, a picture
for it in `drawMissionIcon` in `js/ui.js`, and a list of destinations in the
`Missions` constructor. Nothing else needs touching.

## Coins

Where they lie is worked out from the map, the same way job destinations are, so
they are never inside a wall and always reachable. Because that calculation is
deterministic, **which coins are currently collected is deliberately not
saved** — only the total is. Every session starts with a full town.

One consequence needed handling: closing the game while standing on a coin and
reopening it used to hand out a free coin every single time. `clearAtStart`
quietly removes whatever you were standing on, without paying for it.

## Playing together

**On the opening screen**, tap the blue button with two people on it. Then:

- **Everybody types a name.** It is asked once, remembered, and drawn on a
  little sign over that player's head. It uses the phone's own keyboard rather
  than a home-made A–Z pad, because a home-made one would have to pick an
  alphabet and the names in this family are not all spelled in the same one as
  the buttons.
- **One of you taps `+`** and is shown a four-digit code. Read it out, tap play,
  and the code stays in the corner of the screen so it can be read again.
- **The other taps the keypad button**, types those four digits, and the game
  starts by itself on the fourth digit.

Codes are digits and not words on purpose: digits are the one kind of text a
6-year-old reliably reads and types.

Everyone joining a room would otherwise appear on the same square, inside one
another, so each player steps aside on arrival — in a direction taken from their
name rather than from chance, so the same person always starts in the same place.

### Or by link

Every game also puts its code in the address, so a game can be bookmarked or its
link shared, and opening such a link goes straight to the name box and then to
playing:

```
https://tauruskin.github.io/taras-town/?room=2398
https://tauruskin.github.io/taras-town/?room=our-secret-name-4821
```

Whoever opens it first hosts; everyone else joins them.

**The code is the only lock on the door.** Anyone who has it — or who guesses
it — can walk in, from anywhere. A four-digit code is deliberately easy for a
child to read out, and that also makes it easy to guess: there are only nine
thousand of them. When you want privacy, use a long made-up name in the address
instead. Room names live in a space shared with every other project using the
same introduction service, so a room called `park` or `taras` is genuinely
likely to be stumbled into. Use something long and made-up, like
`maple-lantern-xoj1zf`, and treat the link like a house key.

### Bumping into each other

Walking into another player **pushes them**, with a small sound so a bump reads
as a person rather than a wall. That is how you find somebody hiding under a
bush: they are shoved out into the open.

Getting this right took two goes, and the second version is the one to keep.
Players were made *solid* first — walk into one and you stop. It found people,
and it also **stuck them together**, because two children pressing into one
another are each blocked by the other; somebody backed into a corner had nowhere
to go at all. It was the same trap the cars used to set.

So:

- **Another player is never a wall.** Nobody can be pinned by anybody.
- **The one who is walking pushes the one who is standing.** That asymmetry is
  the whole trick. When both back away at once they settle at arm's length and
  the walker can never reach the hider, which is a soft wall that gives nothing
  away.
- **Nobody is moved by anybody else.** Each player only ever moves themselves,
  on their own device, through the ordinary movement code — so walls still stop
  the push and no position is ever forced. Both devices do it, so the shove is
  mutual.
- Somebody **driving** is left alone. A vehicle is big and fast enough to barge
  a child along a wall, which is the one thing this must never do.

`tests/browser/bumping.mjs` checks both halves: that a bump moves somebody, and
that **nobody can ever be stuck** — including someone leaned on while backed
against a wall.

### Same wifi, or anywhere?

**Same wifi: reliable.** The devices talk straight to each other and nothing
else is involved.

**Different places: usually works, but not guaranteed.** When two devices cannot
reach each other directly — which depends entirely on the two routers or mobile
networks involved, and is nothing to do with this game — the connection falls
back to a relay run by the makers of the library. That is a free shared service
with no promises attached, so it may be slow or unavailable.

### What goes through somebody else's server

An **introduction service** is always used. A browser cannot listen for incoming
connections on its own, so something has to tell the two browsers how to find
each other.

A **relay** is used only when a direct connection cannot be made. On the same
wifi this never happens. When it is used, positions and names do travel through
somebody else's server.

`js/vendor/peerjs.min.js` is the only third-party code in the project. It is
checked in rather than loaded from a CDN, and **it is only downloaded when there
is a `?room=` in the address**. Playing on your own never fetches it.

### What crosses the wire, and what does not

Exactly one piece of typed text crosses the wire: **the name a player chose for
themselves.** It is capped at ten characters, stripped of control characters,
and cleaned at both ends, because nothing arriving over a network is trusted.

Everything else is where somebody is and what colour their hat is.

**There is still no chat**, no second message, and no way to send words or
pictures after that name. There is no channel down which a conversation could
happen. `tests/offline/net.mjs` pins the exact list of fields and fails if
another piece of text ever appears — it was written to be extended
consciously and never loosened.

There is **no profanity filter**. Rooms are shared by a code between people who
know each other, which is the judgement this rests on; if strangers ever end up
in a room, a name is the one thing they can put on your child's screen.

Coins, jobs and unlocks stay entirely on each phone. Nobody can spend anybody
else's coins.

### It looks after itself

Whoever opens the link first hosts, and that claim is released when they close
the game or their phone locks. Everyone else notices within a few seconds, waits
a moment, and tries again — at which point one of them simply becomes the new
host and play carries on. **Nobody ever has to reload anything.** When the
original player comes back they join as an ordinary guest.

Switching away from the game stops your character moving for everyone else, and
after a few seconds the others stop showing you. Switch back and you reappear.

### Phones, tablets and computers

Any of them, and mixed together: a phone and a laptop can play in the same town.
Tested on the live site with a phone-shaped browser and a desktop-shaped one.
